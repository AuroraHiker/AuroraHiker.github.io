第一次尝试把代码打包成一个 `class` 的时候，笔者其实还不知道软件工程里这些最基本的原则。

那时做事的逻辑并不混乱，脑子里很清楚该输入什么数据、经过哪些步骤、最后输出什么结果。可惜注意力全放在了让代码“一步一步跑起来”上，反而忽略了它日后该如何修改、扩展和排查问题。

于是，那个最初版本的类很快就变成了一团“意大利面条”：

- 没有留出多余的接口，后面想加功能只能硬塞；
- 函数之间互相依赖太多，改一个地方会牵动一整片；
- 变量命名不够明确，过几周再看，连自己都要重新猜它的含义；
- 一些中间结果到处传递，谁改了数据、在哪里改的，排查起来非常痛苦；
- 到了后期，维护几乎等于重写。

这段经历之后，笔者才真正意识到：编程能力并不只由逻辑、语法、数据分析、算法构成。它们当然重要，但如果你想让代码长期可用、可改、可交给别人看，就必须补上软件工程这门课。

后来，借由这些基本原则，再配合充分而合理的注释、{% post_link Git-简明教程：写给个人开发者的代码时间线管理指南 Git 版本管理 %}和更清晰的项目结构，笔者几乎不再需要在维护此前的代码中反复“考古”。每当想起当年那段经历，都不由得感慨：论屎山是如何练成的，答案往往不是“这个人不会写代码”，而是“这个人考虑了今天能不能跑，或许还考虑了以后能不能用，但他一定没考虑以后还能不能改，尤其是大改”。

这篇文章就从开发者最容易踩坑的角度，聊聊软件工程里非常基础、但非常有用的 7 个原则：抽象、模块化、信息隐蔽、局部化、一致性、完备性和可验证性。

它们听起来有点像教材里的大词，但落到日常写代码里，其实都很朴素：让复杂问题变简单，让不同代码各司其职，让修改范围尽量变小，让 Bug 更容易被发现。

# 1. 抽象

## 1.1 先看“做什么”，再看“怎么做”

抽象，就是把复杂问题暂时“折叠”起来，只暴露当前层次最需要关心的内容。

很多初学者写代码时，常常会把所有细节堆在一起：读文件、清洗数据、计算指标、画图、保存结果，全都写在同一个脚本里。这样做在最开始很爽，因为你能从上到下一口气写完。但代码一长，问题就来了：你很难说清楚某一段到底负责什么，也很难单独替换其中一个步骤。

抽象的思路是反过来的：先从高层流程看问题，再逐层细化。

比如你想写一个数据分析脚本，不要一上来就把所有细节写进主程序，而是先把流程拆成几句话：

```python
"""
数据分析脚本

输入数据：
- data.csv：原始 CSV 数据文件，至少包含后续清洗和分析所需字段 (笔者通常会在此注明必须的列)。

输出数据：
- result.csv：保存分析结果的 CSV 文件 (笔者通常会在此注明新增和删减的列)。

数据处理流程：
1. load_data() 读取原始数据；
2. clean_data() 清洗缺失值和异常值；
3. analyze_data() 对清洗后的数据进行统计或建模分析；
4. save_result() 将分析结果保存到指定文件。
"""
data = load_data("data.csv")
cleaned_data = clean_data(data)
result = analyze_data(cleaned_data)
save_result(result, "result.csv")
```

这段代码哪怕不看函数内部，也能大致理解整个程序在做什么：

- `load_data()` 负责读取数据；
- `clean_data()` 负责清洗数据；
- `analyze_data()` 负责分析；
- `save_result()` 负责保存结果。

这就是抽象的价值：你先把程序看成几个清楚的动作，而不是一大堆细节。

等高层流程稳定之后，再去填充每个函数内部的实现：

```python
def clean_data(data):
    """
    清洗原始数据

    Args:
        data: 原始 DataFrame，至少包含列 "age"。

    Returns:
        删除缺失值并过滤 age < 0 之后的新 DataFrame。
    """
    data = data.dropna()
    data = data[data["age"] >= 0]
    return data
```

这里的 `clean_data()` 就是下一层细节。调用它的人不需要知道内部到底用了 `dropna()`，还是用了别的清洗方法。调用者只需要知道一件事就足够了：传入原始数据，得到清洗后的数据。

可能有读者朋友会想：我是个人开发者，调用者和维护者都是我自己，有必要把这些细节写得这么清楚吗？

笔者的建议是：很有必要。绝大多数人并不能清楚记住自己几年前写过的脚本细节，能记住大致用途就已经不错了。注释和文档字符串的价值，正是在你几年后再次打开这个脚本时，帮助你迅速意识到当时在做什么、哪个函数负责哪一步、哪些代码可以直接复用，哪些地方需要谨慎修改。

## 1.2 从补丁思维到结构思维：抽象为什么能减少 Bug？

野生程序员往往很擅长“解决眼前问题”。数据格式乱了，就立刻写几行代码修一下；结果不对，就顺手加几个判断；文件保存出错，就临时改一下路径。这种能力非常实用，也是很多个人开发者能快速把项目跑起来的原因。

但问题在于，如果每一次修改都只是“哪里坏了补哪里”，代码很快就会变成一连串临时补丁。更麻烦的是，这些补丁往往没有注释、没有边界检查，也没有明确职责。时间一长，你看到的就不再是一个清晰的程序，而是一团“当时好像能跑”的历史遗迹。

抽象的价值，就在于把这种“补丁思维”升级成“结构思维”。

这时你不再只是想“这里要加三行代码”，而是会进一步追问：

- 这三行代码到底在解决什么问题，属于读取、处理、分析还是输出？
- 这个逻辑以后会不会重复出现？
- 它应该放进已有函数或类里，还是应该单独抽成一个新函数？
- 可能出现哪些非法输入、异常数据或边界情况？
- 调用者真正需要知道哪些细节，哪些细节应该被隐藏起来？

当你开始这样思考，代码就不会越写越散，而是会逐渐长出清晰的骨架。你写下的不再只是一个个临时修补点，而是一套可以理解、可以复用、也可以继续扩展的结构。

这也正是抽象能减少 Bug 的原因：它减少了你同时需要处理的细节数量。

人脑的工作内存是有限的。如果一个函数里同时出现文件路径、数据清洗规则、统计公式、绘图样式和保存逻辑，你在改其中任何一处时，都可能不小心影响另一处。抽象之后，每一层只关注自己的问题：读取函数只负责读取，清洗函数只负责清洗，分析函数只负责分析，保存函数只负责保存。每个部分的职责越清楚，修改时的影响范围就越小，Bug 自然也更容易被发现和控制。

简单说，抽象不是为了把代码写得“高级”，而是为了让你在修改代码时不用一次性面对整个世界。它让你从“临时修一下”变成“想清楚这段逻辑应该属于哪里”，而这一步，往往就是代码从难维护走向可维护的开始。

# 2. 模块化：把一大坨程序拆成能独立工作的零件

模块化，就是把复杂系统拆成多个相对独立的模块。每个模块负责一类事情，模块之间通过清晰的接口协作。

如果说抽象强调“从高到低看问题”，那么模块化强调“把不同职责分开放”。

## 2.1 从单文件到多模块

一个常见的项目可能长这样：

```text
project/
  main.py
```

所有代码都在 `main.py` 里。刚开始只有几十行，问题不大。但随着需求一点点增加，`main.py` 里会慢慢塞进路径配置、数据读取、数据清洗、统计分析、画图保存、临时调试代码。它会从“主程序入口”变成“万能收纳箱”：什么都能往里扔，但真要找东西时很痛苦。

更好的方式，是按职责拆成多个文件：

```text
project/
  main.py
  config.py
  data_loader.py
  preprocessing.py
  analysis.py
  visualization.py
```

每个文件只负责一类事情：

- `config.py` 放路径、参数、常量；
- `data_loader.py` 负责读取数据；
- `preprocessing.py` 负责预处理；
- `analysis.py` 负责核心分析；
- `visualization.py` 负责画图；
- `main.py` 只负责任务编排。

这样做以后，主程序会变得很清爽：

```python
"""
main.py：鸢尾花数据分析任务入口

输入数据：
- config.RAW_DATA_PATH：原始数据文件路径，要求包含 species、sepal_length、sepal_width 等字段。

输出数据：
- config.FIGURE_PATH：分组统计图保存路径。

模块分工：
1. data_loader.load_iris_data() 负责读取数据；
2. preprocessing.clean_iris_data() 负责清洗和字段校验；
3. analysis.calculate_species_summary() 负责按物种统计；
4. visualization.plot_species_summary() 负责绘图和保存。
"""
from analysis import calculate_species_summary
from config import FIGURE_PATH, RAW_DATA_PATH
from data_loader import load_iris_data
from preprocessing import clean_iris_data
from visualization import plot_species_summary


def main():
    """
    按固定顺序执行完整分析流程。
    """
    raw_data = load_iris_data(RAW_DATA_PATH)
    cleaned_data = clean_iris_data(raw_data)
    summary = calculate_species_summary(cleaned_data)
    plot_species_summary(summary, FIGURE_PATH)


if __name__ == "__main__":
    main()
```

这段代码本身并没有变“高深”，但它的意图清楚了很多。你不需要把所有细节都摊在眼前，只要看函数名和模块名，就能知道这套程序的大致走向。

## 2.2 模块化不是文件越多越好

模块化很容易被误解成“拆得越碎越专业”。但拆分本身不是目的，边界清楚才是目的。

如果一个项目只有一百行代码，却被拆成十几个文件，每次读代码都要在文件之间来回跳，那只是把复杂度从文件内部搬到了文件之间，维护成本并不会真的下降。模块化的关键不在于文件数量，而在于职责边界是否清晰。

一个简单的判断标准是：如果两个函数经常因为同一个原因一起变化，它们大概率应该留在同一个模块里；如果它们变化的原因完全不同，就应该考虑分开。

比如：

- 数据读取逻辑变了，通常不应该牵动画图逻辑；
- 画图配色变了，通常不应该影响统计计算；
- 保存文件路径变了，通常不应该改动模型算法；
- 参数默认值变了，通常应该集中在配置文件里，而不是散落在每个函数内部。

模块拆得过细，你会疲于在文件间来回切换；拆得不足，一次改动又可能波及大片代码。真正恰当的模块化，是让每一次变化尽量停留在局部，不轻易扩散。

## 2.3 为什么模块化能事半功倍？

因为模块化让代码可以被替换、复用和单独检查。

如果数据读取出了问题，你可以只看 `data_loader.py`；如果图画得不对，你可以只看 `visualization.py`；如果统计结果异常，你可以只检查 `analysis.py`。问题被限制在更小的范围内，Debug 自然会快很多。

更重要的是，模块化会逼你想清楚接口。比如 `clean_iris_data()` 接收什么、返回什么，`plot_species_summary()` 需要哪些列、保存到哪里，这些问题一旦清楚，模块之间的协作就不再依赖“我应该记得这里怎么写过”，而是依赖稳定的输入输出。

当你把每个模块都做成一个能独立理解的小零件，维护代码就会从“翻一整座山”变成“检查某一块零件”。这就是事半功倍的地方。

对野生程序员来说，模块化的另一项收益，是让你开始积累自己的工具箱。今天写的 `data_loader.py`，明天换一个分析任务也许还能用；今天整理好的 `visualization.py`，以后换个数据集也许只需要改一点参数。这是从“写一次脚本”到“沉淀一套工作流”的关键步骤。

# 3. 信息隐蔽

## 3.1 为什么要将模块设计为“黑箱”？

信息隐蔽 (也称信息封装) 的核心思想是：模块应像一个“黑箱”，外部只能通过公开接口与其交互，而不应依赖其内部实现细节。

这一原则听起来像是大型项目才需要关注的，但在个人脚本中同样常见。我们用一个简单例子来说明。

假设你写了一个用户信息类：

```python
class User:
    """反例：直接暴露 age 字段，外部可以绕过校验写入非法年龄。"""

    def __init__(self, name, age):
        self.name = name
        self.age = age
```

如果外部代码可以随便改它：

```python
"""
反例调用：直接修改对象内部字段，会破坏业务规则。
"""
user = User("Alice", 18)
user.age = -100
```

从语法上看，这没有问题。但从业务角度看，年龄显然不应该是负数。如果任何地方都能直接修改 `age`，很难保证数据始终合法。

更稳妥的做法，是把修改行为收进类内部，由类自身负责校验：

```python
class User:
    """用户信息对象，负责维护年龄的合法性。

    Attributes:
        name: 用户名。
        _age: 内部保存的年龄，外部不要直接访问。
    """

    def __init__(self, name, age):
        self.name = name
        self._age = None
        self.set_age(age)

    def set_age(self, age):
        """设置年龄，并拒绝非法输入。"""
        if age < 0:
            raise ValueError("age cannot be negative")
        self._age = age

    def get_age(self):
        """返回当前年龄。"""
        return self._age


# 正例调用：通过公开方法修改年龄，校验逻辑会被统一执行。
user = User("Alice", 18)
user.set_age(20)
```
> 在 Python 里，单下划线开头的变量比如 `_age` 并不会被真正禁止访问，它更多是一种约定：表明这是内部细节，提示外部代码不要随意修改。

表面上看，这样只是把校验逻辑集中管理起来了。但如果只把眼光停留在“校验”上，就远远低估了“黑箱”设计的真正价值。

把 `_age` 藏进类内部，更深层的意图在于三点：

1. **隔离变化**：假如未来需求变更，年龄不再由外部传入，而是改由系统内部基于出生日期自动计算。系统内部新增一个 `_birth_date` 字段和 `_age_calibrated` 记录，`__init__` 时用 `_birth_date` + 当前日期自动计算年龄并写入 `_age_calibrated`，后续 `set_age()` 只用于人工校准 (修正因日期边界产生的误差) ，每次校准都会产生一条校准日志供审计使用。`get_age()` 始终返回当前最新的年龄值。经历上述所有修改后，外部调用方看到的依然是 `user.set_age(20)` 和 `user.get_age()`，接口完全不变，调用代码一行都不用改——内部从“单纯存一个数字”变成了“自动计算+人工校准+审计日志”的完整机制，但对外只暴露最朴素的两个方法。

2. **降低认知负担**：外部调用者只需记住 `set_age()` 和 `get_age()` 这两个稳定的接口，有且仅有这两个入口，认知负担降到了最低。至于内部是用普通字段、字典还是数据库存储的，数据是手动传入的还是基于出生日期自动计算的，调用者一概不必关心。

3. **集中控制权**：所有修改入口都经过同一道“城门”，校验、日志、权限检查都可以在这里统一添加。比如将来要加一条“年龄不能超过150岁”的规则，只需改 `set_age()` 一处，所有调用自动生效。

这就是“黑箱”的本质：**对外承诺一个不变的契约 (接口) ，对内保留自由演进的余地 (实现) **。无论脚本规模大小，这种思维都能让你在改动时少踩坑。综上，黑箱不是为了保持神秘，而是为了更好地应对变化。这也正是开篇所说“外部不应依赖其内部实现细节”的深层含义。

## 3.2 信息隐蔽的边界

上一节展示了“黑箱”设计带来的收益：接口稳定、认知负担低、控制权集中。但“黑箱”到底隐藏了什么？不隐藏什么？这一节专门划清这条边界。

信息隐蔽所隐藏的，是**实现细节**，而非功能本身。换句话说，模块对外公开的是“做什么”，不公开的是“怎么做的”。

站在外部调用者的角度，这个边界划分得非常清楚：

应当了解的信息包括：

- 这个模块能做什么；
- 应该传入什么；
- 会返回什么；
- 出错时可能抛出什么异常。

而不必依赖的的信息则包括：

- 内部变量叫什么名字；
- 内部用了几个临时步骤；
- 内部数据结构以后会不会更换；
- 内部具体调用了哪个第三方库。

这么说比较抽象，我们看一个函数级别的例子：

```python
def save_result(result, output_path):
    """保存分析结果到 CSV 文件。

    Args:
        result: 分析结果表，pandas.DataFrame 类型。
        output_path: 输出文件路径，字符串。

    Raises:
        OSError: 当文件无法写入时抛出。
    """
  
    result.to_csv(output_path, index=False)

# 调用
save_result(result, "output.csv")
```

调用者只需要知道三件事：**传入什么、得到什么、可能出什么错**。至于函数内部用的是 `pandas.to_csv()` 还是 Python 自带的 `csv` 模块，调用者不必关心，也不应该依赖。这正是“信息隐蔽”的边界所在——**接口是承诺，实现是细节，承诺对外稳定，细节对内自由。**

为什么这条边界如此重要？因为依赖接口的代码是安全的 (接口变更往往意味着整个模块功能的重新设计，这类变更在项目中是受控且克制的) ，而依赖实现的代码是脆弱的 (实现细节可以随时因性能优化、Bug 修复或需求调整而改动) 。把边界划清楚，两边的自由度都最大：调用方只记承诺，开发者只改细节，互不牵制。

## 3.3 把变化锁进黑箱

前两节我们分别讨论了黑箱的收益 (封装过程以换取稳定的接口) 和边界 (外部使用者只需关注输入、输出和异常约定) ，这一节来看具体落地：如何用接口把变化真正封锁在模块内部。

在快速开发中，开发者常常直接操作中间变量，因为这样写起来最快：

```python
"""
反例：外部代码直接修改 pipeline 内部数据。

隐患：
- raw_data 的类型、列名或存储位置一旦变化，这段代码就会失效；
- 分数标准化规则散落在外部，后续很难统一调整。
"""
pipeline.raw_data["score"] = pipeline.raw_data["score"] * 100
```

短期看确实便捷，但隐患随之而来：`raw_data` 的类型、列名或存储位置一旦变化，所有直接访问它的外部代码都会损坏；分数标准化规则如果散落在外部各处的脚本里，后续想统一调整时就会疲于奔命。

更好的做法是把操作收进模块内部，对外只暴露一个有明确语义的方法：

```python
# 正例：通过公开方法触发分数标准化
pipeline.normalize_score()
```

外部调用者只需要知道“我要把分数统一到百分制”，至于内部是找到分数字段、处理缺失值还是完成单位转换，调用者一概不必关心。即使未来 `raw_data` 从 `DataFrame` 换成其他数据结构，只要 `normalize_score()` 这个方法的语义不变，外部代码就无需跟着改动。

这就是信息隐蔽的终极目标：**将变化牢牢封锁在模块内部。**内部无论怎样重构：换数据结构、换第三方库、换算法实现。只要对外接口保持稳定，外部代码就稳如泰山。当你想要优化内部实现时，不会出现十几个地方都在偷偷访问内部变量的窘境——信息隐蔽让你在重构时只需面对一个模块，而不是无穷无尽的补丁。

# 4. 局部化：让修改只发生在该发生的地方

局部化与黑箱设计一样，都是模块化思想的自然延伸。如果说黑箱设计侧重兼顾使用者的体验与开发者的维护成本，那么局部化则更聚焦于开发者的日常维护体验，其目标直截了当：**尽可能缩小修改波及的范围。**

局部化的核心原则可以概括为：**模块之间松散耦合，模块内部高度内聚。**

这里有两个关键词值得拆解：

- **耦合**：衡量模块之间相互依赖的程度。耦合度越高，一个模块的变动就越容易牵动另一个模块，修改成本随之上升。
- **内聚**：衡量模块内部各成员是否围绕同一职责紧密协作。内聚度越高，模块就越像一个目标清晰、专注做一件事的整体。

编写易于维护的代码，归根结底就是追求一种理想状态：**低耦合，高内聚。**

## 4.1 高耦合："链式反应"是如何炼成的

当模块之间缠绕着过多隐性的依赖关系时，代码就失去了"各自为政"的独立性，变成了一套互相牵制的系统。一处修改如同触发链式反应，沿着隐式的依赖链层层扩散，波及范围难以预判。要理解高耦合的触发机制，先从两个典型场景看起。

**场景一：函数隐式依赖外部全局变量**

```python
# 反例：依赖外部全局变量，参数列表看不出来。

import pandas as pd

file_path = "data.csv"
threshold = 0.8


def load_and_filter_data():
    """读取固定 CSV，并保留 score 大于全局阈值的记录。"""
    data = pd.read_csv(file_path)
    return data[data["score"] > threshold]
```

这个函数依赖了外部全局变量 `file_path` 和 `threshold`。从参数列表看，它似乎"无牵无挂"，调用起来很轻便；但实际上，函数的行为不再由调用者完全控制，而是受制于全局状态。这种设计让函数与外部环境形成了**高耦合**，任何对全局变量的修改都可能在不经意间改变函数结果，而问题的根源却可能隐藏在远离调用处的代码中。

改进方案非常简单：**将所有依赖通过参数显式传入**，让函数的输入输出完全透明。

```python
# 正例：依赖通过参数显式传入。
import pandas as pd

def load_and_filter_data(file_path, threshold):
    """
    读取指定 CSV，并保留 score 大于阈值的记录。

    输入数据：
    - file_path：CSV 文件路径；
    - threshold：筛选阈值，通常为 0 到 1 之间的小数。

    输出数据：
    - filtered_data：筛选后的 pandas.DataFrame。
    """
    data = pd.read_csv(file_path)
    return data[data["score"] > threshold]
```

现在，函数需要什么依赖，调用者从签名中一目了然。

**场景二：类内部多个方法共享可变状态，调用顺序决定结果**

比全局变量的隐性调用更隐蔽的一种耦合，常发生在类的多个方法 (或同一脚本的多个函数) 之间——它们通过共享的可变状态 (即多个方法可以修改的同一个变量) 形成了隐形的时序依赖。

```python
"""
反例：类内部多个方法共享可变状态，调用顺序决定结果。

输入数据：
- 通过 add_item 逐个添加商品；
- 通过 apply_discount 设置折扣率；
- 通过 calculate_total 计算总价并写入 _total；
- 通过 generate_invoice 生成发票，依赖 _total 已被 calculate_total 设置。

问题：
- generate_invoice 与 calculate_total 存在隐式调用顺序依赖：
  调用者若忘记先调 calculate_total，generate_invoice 返回错误结果且不报异常；
- _total 的写入与读取分散在不同方法中，阅读 generate_invoice 源码时，易忽略它依赖 calculate_total 的调用；
- 修改 calculate_total 时，难以静态判断还有哪些方法依赖 _total，修改影响面需要人工追踪，维护成本高。
"""

class OrderProcessor:
    def __init__(self):
        self._items = []
        self._discount_rate = 0.0
        self._total = 0.0

    def add_item(self, name, price, quantity):
        self._items.append({"name": name, "price": price, "quantity": quantity})

    def apply_discount(self, rate):
        self._discount_rate = rate

    def calculate_total(self):
        """计算订单总价，结果写入 _total 供后续方法使用。"""
        subtotal = sum(item["price"] * item["quantity"] for item in self._items)
        self._total = subtotal * (1 - self._discount_rate)
        return self._total

    def generate_invoice(self):
        """
        生成发票。依赖 _total 已被 calculate_total() 设置。
        若调用顺序错误，将产生错误的空发票。
        """
        if self._total == 0.0:
            return "Invoice: No items"
        return f"Invoice: Total ${self._total:.2f}, Discount: {self._discount_rate*100}%"
```

```python
# 调用者可能这样用：
processor = OrderProcessor()
processor.add_item("Book", 20.0, 2)
processor.add_item("Pen", 5.0, 3)
processor.apply_discount(0.1)
invoice = processor.generate_invoice()  # 忘记先调用 calculate_total！
print(invoice)  # 输出 "Invoice: No items" —— 结果错误，但不报异常
```

这种耦合比全局变量更隐蔽，因为所有依赖看起来都是"合法的"成员变量，但问题出在**修改顺序敏感**和**状态在方法间隐式传递**上。

改进的核心是**消除隐式状态传递，让每个方法只依赖自己的参数**：

```python
"""
正例：消除共享可变状态，依赖关系显式化。

输入数据：
- 通过 add_item 添加商品；
- 折扣率作为参数传入计算方法，而非存储在对象状态中。

设计意图：
- 每个方法的输入输出清晰明确；
- 方法之间不存在调用顺序依赖；
- 任意方法可单独调用，返回正确结果；
- 修改折扣逻辑不会波及 generate_invoice。
"""
class Order:
    def __init__(self):
        self._items = []

    def add_item(self, name, price, quantity):
        """添加商品到订单。"""
        self._items.append({"name": name, "price": price, "quantity": quantity})

    def calculate_total(self, discount_rate):
        """
        计算订单总价。
        """
        subtotal = sum(item["price"] * item["quantity"] for item in self._items)
        return subtotal * (1 - discount_rate)

    def generate_invoice(self, discount_rate):
        """
        生成发票。自行调用 calculate_total 计算，不依赖任何预先设置的状态。
        """
        total = self.calculate_total(discount_rate)
        return f"Invoice: Total ${total:.2f}, Discount: {discount_rate*100}%"
```

改进后的版本消除了共享的可变状态，`generate_invoice` 直接调用 `calculate_total` 获得计算结果，因此调用顺序不再重要，即便单独调用也能正确执行。同时，依赖关系通过显式的函数调用而非共享变量传递，后续修改时只需沿调用链追溯，影响范围清晰可辨。

<details>
<summary><strong>💡 思考：函数内部调用另一个函数，这算不算高耦合？</strong></summary>

<br>

**不一定，关键看调用方式和依赖对象。**

| 情况 | 是否高耦合 | 原因 |
|---|---|---|
| A 调用 B，B 是 A 的同类方法，职责相关，仅一层调用 | **否** | 正常的内部协作，B 是 A 实现细节的一部分 |
| A 调用 B，B 来自另一个模块，但依赖的是 B 的公开接口 | **否** | 依赖的是契约而非实现，符合依赖倒置原则 |
| A 调用 B，B 又调用 C，C 又调用 D，形成长调用链 | **是** | 修改底层逻辑可能影响整条链上的所有调用者 |
| 多层调用中，中间某层依赖共享状态或全局变量 | **是** | 隐式依赖层层传递，调用者无法独立理解某一层的行为 |

回到正例中的 `generate_invoice`：

```python
def generate_invoice(self, discount_rate):
    total = self.calculate_total(discount_rate)  # 调用同类方法
    return f"Invoice: Total ${total:.2f}"
```

这里调用 `calculate_total` 是**合理的内部依赖**，原因有三：
- **调用链只有一层**，不继续往下嵌套；
- **依赖的是方法返回值**，而非共享状态——`generate_invoice` 只拿结果用，不关心 `calculate_total` 内部怎么算；
- **职责关联自然**：发票本身就应该包含总价，调用 `calculate_total` 是顺理成章的分工。

**那什么时候会出问题？** 看这个写法：

```python
def generate_invoice(self, discount_rate):
    tax = self._get_tax_rate()                     # 第1层
    subtotal = self._calc_subtotal()               # 第1层
    total = self._apply_discount(subtotal, discount_rate)  # 第2层
    final = self._apply_tax(total, tax)            # 第3层
    return self._format_invoice(final)             # 第4层
```

问题在于：
- 修改 `_get_tax_rate`，整条链上的方法可能都要跟着改；
- 要理解 `generate_invoice` 干了什么，得顺着调用链往下读好几层；
- 这些辅助方法可能被其他方法调用，改一个影响多个调用方。

**经验性判断标准**：
- 调用链 **≤ 2 层**，且每一步都有明确的输入输出 → 通常没问题；
- 调用链 **≥ 3 层**，或中间有共享状态传递 → 考虑重构。

</details>

综合上述示例不难发现，高耦合容易引起**修改的影响沿隐式依赖链扩散，触发链式反应，波及范围不可预判**。而局部化的改进方向也一致：**消除隐式依赖，让所有依赖关系显式化**——要么通过参数传递，要么通过明确的返回值衔接。这样一来，修改的涟漪就能被限定在模块边界之内，链式反应在此被截断。

## 4.2 低内聚：“多管闲事”的模块

低内聚的典型表现，是一个模块里混杂了过多互不相关的职责——说白了就是**管得太宽**。比如一个函数同时负责读数据、清洗数据、训练模型、画图、发邮件，它的问题不在于代码行数多，而在于什么事都想插一脚。

这种“多管闲事”的设计带来两个直接后果：

- **理解成本高：**阅读者必须消化与当前目标无关的细节才能理解整个模块；
- **修改风险大：**改一处功能，可能触及大半个模块的代码。

更好的做法是让不同职责各归其位，是把低内聚函数的不同行为拆开，把不同职责委托给专门的函数完成。

回到低内聚的本质：当一个模块"多管闲事"时，它就成了修改的汇集点。外部需求变动可能牵连到它，对它自身的修改也可能波及它曾管过的那些事。而高内聚让每个模块只专注一件事，修改的涟漪被控制在内部，这正是"局部化"追求的效果。

## 4.3 让结构化成为你的外置大脑

很多单人项目的最大风险，就是"全局变量到处飞"和"函数互相乱调"。开发初期只有自己刚写的代码，当然记得哪些变量在哪里被改过。可项目搁置两个月后再回头看，你就会变成一个陌生的读者。

局部化的意义，就是把本该由你记住的事情，交给结构来承载。

如果一个函数的输出只由输入决定，它出错时，排查范围天然被限定在函数内部，你不需要记住它依赖了哪些外部状态。但若一个函数既修改全局变量，又写文件，又更新界面，又改变对象状态，还顺手调用其他函数，它一旦出错，你必须在脑海中重建它走过的每一条路径，才能判断究竟是哪一步偏离了预期。这时候，你的大脑成了唯一的调试器。

局部化的目的，就是把这个调试负担从人脑卸载到代码结构上。当每个模块的影响范围足够小时，修改一个函数，你能清晰判断它影响哪里、不影响哪里。Bug 的传播路径变短了，排查成本自然也会下降。

代码不是靠人的记忆力撑起来的。当结构足够规整时，函数签名本身就是最可靠的文档——它清楚告诉你依赖什么、返回什么、可能影响什么。由此，开发者能从琐碎的细节中抽身，把有限的注意力留给真正需要判断的问题。

# 5. 一致性：让代码形成统一的"语言体系"

一致性，是指整个软件系统使用一致的概念、符号和术语。

这条原则看起来最简单，却最容易被低估。很多代码变难维护，并不是因为算法多复杂，而是因为命名和风格混乱.

比如同一个用户编号，在代码里同时出现 user_id、uid、account_number 三种写法。读者每次遇到它们，都不得不额外判断一次：这三个变量是不是同一个东西？这种判断单次成本不高，但累积起来就是巨大的认知损耗。

一致性要解决的核心问题只有一个：消除歧义。

## 5.1 一致性的具体表现

一致性至少体现在这些地方：

- 命名风格一致；
- 同一概念使用同一个词；
- 文件和目录结构一致；
- 函数参数顺序一致；
- 返回值格式一致；
- 错误处理方式一致；
- 注释风格一致。

比如你决定项目里统一用 `user_id`，就不要一会儿写 `uid`，一会儿写 `userID`，一会儿写 `account_id`。

函数命名也是同样的道理。如果约定读取函数统一使用 `load_` 前缀，就尽量保持：

```python
load_user_data()
load_config()
load_experiment_result()
```

而不要混成：

```python
load_user_data()
read_config()
get_experiment_result_from_file()
```

这些名字单独看都不算错，但混在一起，调用者就很难凭名字快速判断函数职责，徒增理解成本。

## 5.2 命名是最简洁的说明文档

变量命名是命名一致性中最常见、也最容易被忽视的一环。

很多初学者喜欢写：

```python
a = 10
b = 20
c = a * b
```

临时计算时这样写没问题，但出现在正式代码里，几周后再读就很难知道 `a`、`b`、`c` 分别代表什么。更好的做法是：

```python
# 功能：计算矩形面积。
width_cm = 10      # 矩形宽度，单位 cm
height_cm = 20     # 矩形高度，单位 cm
area_cm2 = width_cm * height_cm  # 矩形面积，单位 cm^2
```

好的变量名能减少注释需求。比如：

```python
valid_users = users[users["age"] >= 18]
```

这行代码本身已经说明了：筛选出年龄大于等于 18 的有效用户。它比 `x = y[y["a"] >= 18]` 好懂得多。

## 5.3 把代码写成自己的说明书

在开发中让代码学会自解释，是一致性带给开发者最直接的回报。

自学编程时，我们很少有人会真正关注一致性问题，通常只求“能跑就行”。可一旦项目规模变大，命名混乱就会迅速成为维护负担。

一致性会让代码形成一套“语言系统”。当你习惯了某种命名方式，写新功能时就不必每次重新发明词汇；读旧代码时，也能更快猜到一个函数或变量的用途。

这种收益的根源在于：一致性减少了猜测。

维护代码时，最耗时的往往不是写新代码，而是理解旧代码。如果命名、结构和返回格式都保持一致，你会更容易建立预期：

- 看到 `load_`，就知道它大概率负责读取；
- 看到 `is_`，就知道它大概率返回布尔值；
- 看到 `to_`，就知道它大概率做格式转换；
- 看到 `validate_`，就知道它大概率做检查。

一致性越强，读代码时的迷茫和疑惑就越少，维护的阻力也越小。

# 6. 完备性：为现实世界构筑应对异常的“防火墙”

完备性，也叫完整性，指软件系统不丢失任何重要成分，能够完整实现系统所要求的功能。

我们写代码时，很容易假设一切顺利：输入正确、文件存在、网络通畅。但现实世界从来不按理想情况运行，软件上线后，会遇到各种不可预测的用户操作、异常环境和外部故障。完备性，就是为这些现实问题准备的一道防火墙——它的目的不是堆砌功能，而是确保每个可能出问题的入口都有对应的处理逻辑。

## 6.1 防御性编程：把问题挡在墙外

写一个功能时，你可以用这几个问题来检验它的完备性：

- 正常输入能正确处理吗？
- 空输入、空值会崩溃吗？
- 错误格式的数据会怎样？
- 依赖的文件不存在怎么办？
- 网络请求失败怎么办？
- 外部数据格式发生变化怎么办？
- 结果保存失败怎么处理？
- 用户重复执行同一个操作会出问题吗？

这些问题不是每个都必须写大量代码来应对，但至少要意识到它们的存在，并做最基本的兜底。

值得强调的是，防御性措施并非采用统一模板机械套用。同样是做检查，检查的内容、位置和方式取决于防御的目标，也就是预判调用时容易出问题的环节：是外部环境可能发生的故障，还是调用方传参不规范。下文通过三个例子进行对比。

先看读取配置文件的场景。很多人只写了文件存在时的正常逻辑，完全没考虑文件不存在时程序应该怎么办。其实多加一行判断，就能挡住这个隐患：

```python
from pathlib import Path
import json
from typing import Union

def load_config(file_path: Union[str, Path]) -> dict:
    """
    从 JSON 文件加载配置。

    若文件不存在，则打印提示信息并返回空字典。
    若文件存在但内容不是合法 JSON，则抛出 json.JSONDecodeError。

    Args:
        file_path: 配置文件的路径 (字符串或 Path 对象) 。

    Returns:
        dict: 解析后的配置字典；文件不存在时返回空字典。

    Raises:
        json.JSONDecodeError: 文件内容格式无效时抛出。
    """
    path = Path(file_path)
    if not path.exists():
        print("配置文件不存在，已使用默认配置")
        return {}
    return json.loads(path.read_text(encoding="utf-8"))
```

这行判断的好处很直接：一旦路径错了，程序能立刻明确报出“文件不存在”，并改用默认配置保证基本可用，而不是等到后面某个地方抛出一个不相关的异常，让人花半天时间去排查。

这个例子防御的外部环境的不确定性——配置文件可能缺失，所以提前检查它的状态，把错误发现在萌芽阶段，避免扩散到系统内部。

再看一个更隐蔽的例子。这个求平均值的函数，看起来没什么问题：

```python
def average(numbers):
    return sum(numbers) / len(numbers)
```

传入正常列表时工作良好：

```python
average([1, 2, 3])  # 返回 2.0
```

但传入空列表呢？

```python
average([])  # ZeroDivisionError: division by zero
```

这就是只考虑了“理想输入”，忽略了边界情况。改进后的版本：

```python
def average(numbers):
    """
    计算一组数的平均值。

    Args:
        numbers: 数值列表，不能为空

    Returns:
        float: 平均值

    Raises:
        ValueError: 当 numbers 为空列表时抛出
    """
    if not numbers:
        raise ValueError("numbers cannot be empty")
    return sum(numbers) / len(numbers)
```

这个判断不是为了让代码变复杂，而是让错误更早、更清晰地暴露出来——出问题时你一眼就知道是“传入了空列表”，而不是面对一个莫名其妙的“分母为零”。

这个例子要防御的，是调用方可能传入空列表这类不合法参数，所以在入口处增加校验，把异常提前拦截在数学运算之前，并给出更明确的报错信息。

第三个例子更进一步，展示了设计好的检查点对快速定位 bug 的价值。很多不完整的代码不会立刻失败，而是拖到后面某个无关的地方才崩溃。比如，真实问题是输入文件缺了一列，程序却一直到画图阶段才报错，这时候你很容易误以为是绘图逻辑出了问题。

如果在进入画图之前，先做一次数据合法性检查：

```python
# 定义当前任务必需的列名
required_columns = {"name", "score"}

# 用集合运算找出数据中缺失的列
missing_columns = required_columns - set(data.columns)

if missing_columns:
    # 尽早抛出明确错误，避免缺列问题蔓延到后续画图等环节
    raise ValueError(f"missing columns: {missing_columns}")
```

错误就会在检查点被提前拦截，而不是等画图时再莫名其妙地崩溃。错误暴露得越早，定位就越容易；错误信息越清晰，调试就越省力。所谓完备性，核心不是写出永远不会出错的代码，而是让错误发生在一个你一眼就能看明白的地方。

这个例子的防御目标是应对外部数据格式的变化，以及调用方传入的数据不完整。它真正的要点不在于检查本身，而在于检查的时机——把问题挡在模块交界处，而不是让它在不相关的位置爆发，再逐个模块往回追溯。


三个例子的防御目标不尽相同：第一个防御的是外部环境的不确定性，第二个防范的是调用方传参不规范，第三个则是在前两者的基础上进一步强调了检查的时机——把问题拦截在模块交界处，而不是放任它跑到不相干的地方再暴露。针对不同的目标分别构筑对应的“防火墙”后，代码的完备性和容错率都会有明显提升。

但也要避免走向另一个极端：完备性不是把所有未来可能发生的事都提前处理完，那叫过度设计。判断的标准很简单——围绕当前功能，把必要部分补齐即可：

- 输入是什么，合法标准又是什么
- 输出是什么，异常情况下返回什么
- 中间失败怎么处理
- 边界情况怎么处理
- 使用者如何知道出错原因

把这五点想清楚，防御性编程就不会变成“每个函数都加一堆 if”。完备性的目的不是预测所有未来，而是划定当前功能的边界，无论是文件不存在还是空列表，真正有效的防御都是让错误在最早的位置、用最明确的方式暴露出来。做到这些，绝大部分问题就已经被挡在墙外了；剩下的由测试和迭代去发现。

## 6.2 先“建房”，再“砌墙”

很多自学开发者都习惯快速开发出能用的代码，这个做法本身没错。但跑通之后如果不回头补边界，代码就只是“演示可用”，而不是“实际可用”。实用主义的顺序是：先写能跑的版本，再回头参考 6.1 中的完备性清单，基于自己项目的具体情况，加上合适的防火墙。

补边界并不需要一次性做完。你可以在主流程跑通后，按“空值、格式错误、外部资源不可用”这三类逐一排查——这三类正是 6.1 清单中最常见也最容易出问题的部分。每补一处，代码就离“实际可用”更近一步。

“先跑通，再补墙”的方式，既保持了开发节奏，又不会让代码长期停留在脆弱状态。完备性不是事后的补救，而是开发流程中自然的一环。当你在入口处多写一行检查，就是在为未来的自己和用户节省大量调试时间。

# 7. 可验证性：让代码容易检查、测试和评审

可验证性，是指软件系统容易被检查、测试和评审，从而确认它是否正确。

测试常常被理解成“大公司才需要的流程”。其实不对。越是单人项目，越需要一点可验证性，因为没别人能帮忙兜底。

可验证性不一定一开始就等于完整的自动化测试框架。它可以从很小的习惯开始：

- 函数输入输出明确；
- 关键步骤能打印或记录日志；
- 每个函数可以单独运行；
- 有几个小样例可以快速验证结果；
- 修改代码后能用 Git 对比差异；
- 复杂逻辑有注释解释意图。

## 7.1 从函数开始搭建可验证的单元

输入输出明确的函数，是最易于测试与审查的单元。比如折扣计算这种逻辑，就很适合拆成一个可以单独验证的单元：

```python
def calculate_discount(price, discount_rate):
    """
    计算商品折后价格。

    输入数据：
    - price：商品原价，必须大于或等于 0；
    - discount_rate：折扣比例，取值范围为 0 到 1。

    输出数据：
    - final_price：折后价格。

    异常情况：
    - price 为负数时抛出 ValueError；
    - discount_rate 不在 0 到 1 之间时抛出 ValueError。
    """
    if price < 0:
        raise ValueError("price cannot be negative")
    if not 0 <= discount_rate <= 1:
        raise ValueError("discount_rate must be between 0 and 1")
    return price * (1 - discount_rate)
```

这个函数不依赖任何外部状态，只根据传入的参数计算并返回结果。你可以随时调用它并验证返回值是否符合预期。上面这段代码有一个明确的输入和输出，所有异常情况都在文档中说明清楚——这正是可验证的基本单元应该具备的特征。

验证的方式也很直接：

```python
# calculate_discount() 的最小自检样例。
assert calculate_discount(100, 0.2) == 80
assert calculate_discount(50, 0) == 50
assert calculate_discount(50, 1) == 0
```

`assert` 是最简单的检查方式：如果条件成立，程序继续运行；如果条件不成立，程序立刻报错。几行 assert 就能覆盖核心逻辑的主要路径，每次修改代码后顺手跑一遍，很多低级错误就能提前发现。

但现实中很多函数并不是这样写的。比如下面这个：
```python
def process_order():
    data = json.load(open("order.json"))
    # 修改 data 中的字段……
    # 计算折扣……
    # 把结果写回 "result.json"
    # 更新全局统计变量……
```

这展示了可验证性的反面，一段根本无法单独验证的代码。这种情况往往出现在函数依赖了太多外部东西——比如固定路径、全局状态、真实文件。想验证，得先准备好 `order.json`，跑完之后还要去检查 `result.json` 和全局变量是否被正确更新。验证一次的成本高、效率低、不可靠，大部分人会选择不验证，而不敢验证的代码，往往是 Bug 最爱的藏身之处。

将其改写为可验证代码的关键，在于**将外部依赖与核心计算分离开来**。

把核心计算逻辑抽成一个独立的函数，只接收输入、返回输出，不碰任何外部状态。前面写的 `calculate_discount()` 就是这种风格。它不读文件、不访问数据库、不修改全局变量，只根据参数返回计算结果。所以只需几行 `assert` 就能确认它是否正常。

这种写法不只方便测试，还会反向塑造你设计代码的方式。一旦养成“把外部依赖推到边缘、把核心逻辑收进纯函数”的习惯，模块边界会自然变得清晰，职责分配也更合理。这并非巧合——可验证性与良好的设计本就是一体两面。下一节会进一步展开这个观点。

## 7.2 可验证性反向驱动设计改善

很多成熟项目会把“能不能测试”当成设计标准。这并非因为他们格外重视测试本身，而是因为“能不能测试”这个要求，会反向驱动开发者把代码写得更清晰。一个可测试的函数天然就是低耦合、高内聚的，它迫使开发者把依赖显式化、把职责单一化、把接口明确化。在这个过程中，设计自然得到了改善，可验证性不是最后才补的事，它从一开始就在塑造代码的质量。

如果你暂时不想引入完整的测试框架，可以先做三件事：

1. 给核心函数写几个 assert，确保关键逻辑的正确性；

2. 保留一份小型测试数据，不需要每次都用几十 GB 的真实数据来调试；

3. 用 Git 管理版本，每完成一个稳定功能就提交一次，方便对比修改前后的差异。

这三件事不复杂，但能极大降低维护时的困难和焦虑感。

严格来说，可验证性本身不一定减少代码中 Bug 的数量，但它能改变 Bug 的生命周期——让它们更早暴露、更容易定位、更不容易重复出现。不可验证的代码，一个 Bug 可能藏几个月才被发现；可验证的代码，Bug 刚出现就会被自检或测试抓住。

这不仅是可验证性的价值，也是贯穿本章所有原则的共同主旨之一：不保证代码不出问题，但保证出问题后能快速定位、明确原因、高效修复。

# 8. 总结

简单总结上述7个基本原则：

| 原则 | 解决的问题 | 合理的操作 |
|------|------------|----------------|
| 抽象 | 同时面对太多细节，容易被绕晕 | 先写高层流程，再逐层填充函数细节 |
| 模块化 | 一段代码管的事情太多 | 按职责拆分文件、函数 |
| 信息隐蔽 | 外部代码随意访问内部细节 | 通过函数和方法暴露稳定接口 |
| 局部化 | 维护时牵一发而动全身 | 减少全局变量，让输入输出明确 |
| 一致性 | 命名和风格混乱，可读性差 | 同一概念始终使用同一个词，同一类操作遵循同一种命名格式 |
| 完备性 | 只考虑正常情况 | 补上边界、异常和必要检查 |
| 可验证性 | 不确定代码是否正确 | 写小样例、`assert`、日志和 Git 提交 |

你会发现，它们指向的是同一个目标：控制复杂性、增强可维护性。

软件工程不是把简单问题复杂化，而是防止复杂问题失控，并通过拆解让复杂问题变得简单。尤其是当代码从几十行增长到几百行、几千行时，这些原则会决定一个项目是能继续演进，还是慢慢变成谁都不敢碰的屎山。

如果你觉得上面这些原则还有点抽象，不妨先从下面这 7 个动作开始：

1. 每个函数只做一件主要的事。
2. 函数名和变量名尽量写清楚，不要滥用 `a`、`b`、`tmp`、`flag`。
3. 尽量少用全局变量，函数需要什么就通过参数传进去。
4. 把读取、处理、分析、输出拆开，不要全部塞进一个函数。
5. 对重要输入做检查，比如文件是否存在、列名是否齐全、列表是否为空。
6. 给核心函数写 2 到 3 个最简单的 `assert`。
7. 每完成一个稳定小功能，就用 Git 提交一次。

这些动作不需要你立刻掌握复杂理论，也不会显著拖慢开发速度。相反，它们能让你后期修改代码时少走很多弯路，同时慢慢建立起软件工程的思维方式。当面对更复杂的问题时，你会自然地知道如何把大问题拆成小问题，逐个击破。

很多人以为写得快就是效率高。但真正的效率，不是一天写一百行代码，而是这一百行代码功能明确、逻辑清晰、可复用——过一个月回头看，你能迅速看懂自己当时写了什么，并能放心地修改或复用。否则，一百行代码可能只是明天需要重写的负担。

# 写在最后

代码像不像“意大利面条”，和开发者是不是科班出身没有绝对关系。科班程序员也可能写出难维护的代码，野生程序员也完全可以写出清晰、稳定、可复用的代码。

区别在于，是否在开发过程中有意识地控制复杂性。

当你学会抽象，就不会被细节淹没；当你学会模块化，就不会把所有逻辑堆成一坨；当你学会信息隐蔽，就能让内部变化不至于波及全局；当你学会局部化，就能把 Bug 关在更小的范围里；当你保持一致性，未来的你就不用反复猜测变量含义；当你补上完备性，代码就能应对更多真实情况；当你重视可验证性，错误就会更早暴露。

这些原则不会让你一夜之间变成架构师，但它们会让你的代码从“能跑”逐步走向“能维护”。而对大多数个人项目来说，这一步已经足够关键。
