# 引言

不知道各位读者是怎样打开这篇博客的？或许是持续关注我更新的朋友顺手点进来，或许是你已经意识到版本管理的重要性，于是在搜索引擎里和这篇文章偶遇。无论你现在是否已经明确知道“代码版本管理”到底有多重要，都请允许我先从自己的经历讲起：为什么 Git 会成为几乎所有开发者绕不开的工具，又为什么它常常不是一开始就被理解，而是在项目逐渐变复杂之后，才显出它的必要性。

这篇文章属于“野生程序员的进化之路”系列。严格说，除引言外，它是这个系列的第二篇正文，因为版本管理正是我入门后最早意识到的问题之一。

最开始，我只是写出了一份很努力完成、代码本身也没有问题的脚本。但后来我找到了更好的方法，或者发现原来的方向走不通，那份代码就只能暂时弃置。于是我想：我最好建一个文件夹，用来收容每一次尝试后被废弃的代码。虽然暂时不用，后面说不定还能参考。

后来，被废弃的代码越来越多，我又意识到这个“收容站”也得分类。虽然大部分脚本来自同一个大项目，但它们解决的功能并不一样：有的是数据清洗，有的是绘图，有的是模型测试，有的是临时验证某个想法。我开始按小项目、小功能继续套文件夹。

再后来，现役代码也开始出现备份需求。为了提高复用性，或者随着项目目标调整，我不得不对当前还在使用的代码做大修。于是我又想：那就给现役代码的版本迭代也建更多文件夹吧。

写到这里，熟悉 Git 的朋友大概已经想抢答了：你为什么不用 Git 呢？

确实。当开发时间继续变长后，我发现这种手工管理方式很快就乱了。脚本命名不够标准，文件夹堆放没有章法，经常找不到自己想要的那一个版本；很多废弃代码最后也没有真的被参考，因为我已经忘了它当时解决的具体问题。更麻烦的是，我只保存了“大修前后”的版本，没有保存日常小修的中间状态。于是某一次小改动把代码改坏之后，我才发现自己找不回原来能跑的版本了。

这些问题都是初学者在真正遇到之前很难提前想清楚的。事实上，我当时愿意建立一个“代码收容站”，已经算是有版本管理意识了。只是这种意识还停留在“多建几个文件夹备份一下”的阶段。

而我当时没有使用 Git 的原因也很简单：那时的我连如何组织一个工作目录都不太清楚，更不用说学习一个看起来需要命令行基础、环境配置基础、还带着一堆陌生术语的软件了。

所以，这篇教程不会假设你已经懂工程化，也不会一上来就把 Git 讲成团队协作里的复杂工具。我们先从最朴素的问题开始：**当你的代码版本越来越多，靠手工文件夹已经管不住时，Git 到底帮你自动管理了什么？**

你可以先把 Git 理解成一个专门为代码设计的“存档系统”。它能为每一次提交过的代码状态建立快照，记录这次修改的作者、时间、说明，以及具体哪些位置发生了变化。这样一来，代码的时间回溯就成为可能。它有点像电子游戏里的存档：你不仅能回到某个存档点，还能给这个存档点写一句说明，告诉未来的自己“这里到底发生了什么”。

这篇文章面向刚开始独立写项目的个人开发者。目标不是把 Git 所有命令讲完，而是先建立一套足够可靠的工作习惯：知道什么时候需要 Git，什么时候需要 GitHub，怎样在 VS Code 里使用原生 Git，以及如何用一条最简单的分支策略管理自己的项目。

# 1. Git + VS Code 的部署与初始化

在开始使用 Git 之前，需要先在本地完成安装和基本配置。本章会带你完成从零到能正常提交代码的所有准备工作，包括安装 Git、设置身份、整理项目目录、初始化仓库以及创建忽略文件。

## 1.1 安装 Git

在 Windows 10/11 上，最常见的安装方式是使用 [Git for Windows](https://git-scm.com/install/windows)。

进入官网后，下载适合自己系统的安装包，并按照默认选项完成安装。安装结束后，打开终端 (或 Git Bash) ，输入：

```bash
git --version
```

如果能看到类似 `git version 2.x.x.windows.x` 的输出，说明 Git 已经安装成功。

## 1.2 初次配置

第一次使用 Git，需要设置你的提交身份，这个信息会写入每一次提交记录中：

```bash
git config --global user.name "你的名字"
git config --global user.email "你的邮箱"
git config --global init.defaultBranch main
```

这里的名字和邮箱会显示在提交历史里，不影响登录 GitHub，但会帮助别人 (以及未来的你) 知道某次修改是谁做的。

如果将来需要更改，也可以重新执行这些命令覆盖之前的配置。

## 1.3 准备项目结构

在初始化 Git 之前，先把项目文件夹整理清晰。对初学者来说，最实用的原则只有一句话：**一个项目一个文件夹，文件夹结构尽量稳定。** 不要把不同项目混在一起，也不要把临时脚本、下载文件、测试结果和正式代码随手堆在同一层目录里。

比较稳妥的做法，是把一个项目拆成几个职责清楚的部分，例如：

```text
project/
├── src/        # 主要代码
├── data/       # 输入数据
├── docs/       # 文档说明
├── output/     # 运行结果
└── tests/      # 测试脚本
```

如果只是一个体量较小的个人项目，也可以先用更简约的划分方式：

```text
project/
├── code/       # 代码
├── data/       # 输入数据
└── output/     # 运行结果
```

这样做的意义，远不止于让目录“看起来整齐”——更关键的是，当 Git 正式接手版本管理时，你能一目了然地分辨哪些是项目的核心源码，哪些是临时或自动生成的附属文件。尤其在数据分析、爬虫、可视化绘图这类容易产生大量中间产物的项目中，清晰的目录结构能有效避免后期被琐碎文件“绕晕”。至于缓存、环境配置、日志、最终输出等无需纳入版本控制的内容，后续统一交由 `.gitignore` 处理即可。

## 1.4 在 VS Code 中初始化仓库

VS Code 自带 Git 支持，通常不需要额外安装插件。只要前面已经正确安装 Git，VS Code 一般就能自动识别。如果左侧没有“源代码管理”图标，或者 VS Code 没有识别到 Git，可以先在扩展面板中搜索 `@builtin git`，确认内置的 Git 扩展处于启用状态。

接下来要注意一个关键点：**请用 VS Code 打开整个项目文件夹，而不是只打开单个代码文件，或者项目里的某个子文件夹。** 只有把完整项目作为工作区打开，VS Code 才能正确识别它的结构，并把它当作一个完整仓库来处理。

打开项目文件夹后，点击左侧的“源代码管理”图标。如果这个项目还不是 Git 仓库，VS Code 会提示你初始化仓库。点击“初始化仓库”后，项目根目录里会出现一个隐藏的 `.git` 文件夹，它就是 Git 保存历史记录的地方。

在 VS Code 的原生 Git 面板里，常见标记和操作大致如下：

| VS Code 界面显示 | 对应 Git 含义 |
| --- | --- |
| 文件旁边的 `M` | Modified，文件已被修改 |
| 文件旁边的 `U` | Untracked，Git 还没有跟踪这个新文件 |
| 点击文件右侧的 `+` | 将文件加入暂存区，等同于 `git add 文件名` |
| 输入提交信息并提交 | 生成一次 commit |
| 左下角的分支名 | 查看、切换或创建分支 |
| “同步更改” | 拉取并推送远程仓库变化 |

在 VS Code 中理解这些标记之后，Git 的基本操作便已具备了初步基础。但在正式提交项目之前，还有一项工作值得提前完成：项目文件夹内的所有内容，并非全都适宜纳入版本控制。诸如缓存、日志、虚拟环境、打包产物、环境配置等文件，大多为运行过程中自动生成，或仅适合保留在本地环境。

因此，在介绍 Git 的核心操作之前，下一小节将专门介绍 .gitignore，即 Git 的忽略规则。

## 1.5 创建 `.gitignore`

`.gitignore` 是一个**纯文本配置文件**，通常放在 Git 仓库的根目录下。它本身不是代码，也不会被运行；它的作用是告诉 Git：哪些文件或目录不需要纳入版本管理。

这一步看似只是“排除文件”，但其实关系到仓库能不能长期保持清晰。一个项目文件夹里能看到的东西，并不都应该进入版本历史。Git 真正需要记录的，是源代码、文档、必要的配置模板，以及那些能帮助你复现项目过程的核心文件；而依赖目录、缓存文件、构建结果、日志文件、本地环境配置等内容，要么可以重新生成，要么只和当前电脑有关，要么包含敏感信息。把这些内容提交进仓库，不仅会让历史记录变得臃肿，也可能带来安全风险。

因此，创建 `.gitignore` 的目的不是为了“少提交一点东西”，而是为了让仓库只保留真正值得长期追踪的内容。简单来说，**能自动生成的、换一台电脑后不一定通用的、或者不应该公开的文件，通常都应该忽略。**

`.gitignore` 的常见规则并不复杂，可以先记住下面几种写法：

| 写法 | 含义 |
| --- | --- |
| `xxx/` | 忽略整个目录 |
| `*.xxx` | 忽略以 `.xxx` 结尾的文件 |
| `xxx` | 忽略名为 `xxx` 的文件或目录 |
| `/xxx` | 只忽略仓库根目录下的 `xxx` |
| `!xxx` | 取消忽略某个已经匹配的文件或目录 |
| `#` | 注释，不会被 Git 当作规则 |

一个常见的 `.gitignore` 可以这样写：

```gitignore
node_modules/   # 前端依赖目录，体积大，可以重新安装
.venv/          # Python 虚拟环境目录
__pycache__/    # Python 自动生成的缓存目录

.env            # 环境变量文件，通常包含密码、令牌等敏感信息
dist/           # 打包输出目录
build/          # 构建输出目录

*.log           # 所有 .log 日志文件
*.db            # 所有 .db 数据库文件
Thumbs.db       # Windows 自动生成的系统文件
```

根据上面的规则可以看出，`node_modules/`、`.venv/`、`__pycache__/`、`dist/`、`build/` 末尾带有 `/`，表示忽略整个目录；`*.log`、`*.db` 使用了通配符 `*`，匹配所有以 `.log` 或 `.db` 结尾的文件；`.env` 则表示忽略所有名为 `.env` 的文件。如果只想忽略仓库根目录下的 `.env`，可以写成 `/.env`。

最后还要注意一点：`.gitignore` 只对**尚未被 Git 跟踪的文件**生效。如果某个文件之前已经提交过，后来才把它写进 `.gitignore`，Git 仍然会继续跟踪它。也就是说，`.gitignore` 不是“删除历史记录”，而是告诉 Git：以后遇到这些未被跟踪的文件时，不要再把它们加入版本管理。

所以，更严谨的做法是：**在项目启动之初，就先梳理好目录结构，紧接着创建 `.gitignore` 文件，最后再正式开始提交代码。** 尤其要格外留意 `.env` 这类文件，它们往往包含密码、API 令牌或私钥等敏感信息，务必妥善处理，避免误提交。

# 2. Git 的使用逻辑、原理与操作详解

在完成安装和初始化之后，这一章将深入讲解 Git 的核心设计思想，包括它如何管理代码时间线、分支的本质是什么，以及每一种常用操作背后的原理和具体用法。理解这些逻辑后，你会发现 Git 的命令不再是孤立的“咒语”，而是一套有章可循的工具。

## 2.1 Git 的核心功能概述

在引言的故事里，我真正需要的不是更多文件夹，而是一套能替我保存历史、解释历史、找回历史的机制。Git 最重要的功能正好可以概括为四件事：

| 功能 | 用途 |
| --- | --- |
| 记录版本 | 保存某个时刻的代码状态，之后可以回看或回退 |
| 比较差异 | 看清楚自己这次到底改了哪些文件、哪些行 |
| 创建分支 | 在不破坏主版本的前提下尝试新功能或大改动 |
| 合并工作 | 功能完成后，把分支上的成果合并到主线 |

普通的文件夹备份只能保存一堆零散版本，比如 `项目-最终版`、`项目-最终版2`、`项目-真的最终版`。它最大的问题不是不能备份，而是这些备份之间缺少清晰关系与说明：你不知道每个版本为什么存在，也很难快速判断它们之间到底差了什么。

Git 保存的不是混乱的文件夹副本，而是一串清晰的提交记录。每一次提交都是一个带说明的代码存档点。你以后不仅能看到“代码变了”，还能看到“哪里变了、什么时候变的、当时为什么要这么改”。

## 2.2 工作区、暂存区、仓库与提交流程

在理解 Git 的具体操作之前，必须先弄清楚三个基础概念，因为所有命令都是围绕它们展开的：

| 概念 | 理解 |
| --- | --- |
| 工作区 | 你正在直接编辑和修改的项目文件夹 (即你电脑上的项目目录)  |
| 暂存区 | 准备放进下一次提交的改动清单 (可以理解为“待提交列表”)  |
| 仓库 | Git 保存完整历史记录的地方 (即 `.git` 目录)  |

一次最基础的提交流程只有两步：

```bash
git add .
git commit -m "说明这次改了什么"
```

`git add .` 表示把当前工作区的所有改动放进暂存区，相当于告诉 Git：“这些改动我要放进下一次提交里。”  
`git commit -m "说明"` 则表示把暂存区里的内容正式保存为一个新的时间点 (即一次 commit) 。

提交完成后，暂存区会重新变空，仓库中会多出一条新的历史记录。此时工作区里的文件仍然是你刚刚提交后的样子，只是 Git 已经把这个状态保存进了仓库。后续你继续修改文件时，新的改动又会重新出现在工作区中，等待下一次 `add` 和 `commit`。

为什么需要“暂存区”这个中间层？因为它让你可以**精细地选择哪些改动进入下一次提交**。比如你修改了三个文件，但只想把其中两个提交，另一个留到下次，就可以用 `git add 文件名` 分别暂存，而不是一股脑全部提交。

在 VS Code 中，这些操作都能通过图形化界面完成。左侧的“源代码管理”面板 (Source Control) 会列出所有被修改过的文件。当你点击文件旁的 `+` 号，就相当于执行了 `git add`；在输入框中写好提交说明并点击提交按钮，就相当于执行了 `git commit`。同时，VS Code 还会用颜色和字母标记来直观区分文件状态——绿色的 `U` 表示新增 (Untracked) ，黄色的 `M` 表示修改 (Modified) ，红色的删除线表示文件已被移除。这意味着，如果你更习惯使用界面操作，大多数情况下并不需要手动输入命令。

![VS Code 控制视图：用于常规 Git 操作的中心枢纽，如临时部署、提交和管理变更](https://code.visualstudio.com/assets/docs/sourcecontrol/overview/overview.png)

| 图形化操作 | 对应命令 | 概念对应 |
| --- | --- | --- |
| 点击文件旁的 `+` 号 | `git add 文件名` | 工作区 → 暂存区 |
| 点击“提交”按钮 | `git commit -m "..."` | 暂存区 → 仓库 |
| 点击“刷新”按钮 | `git status` | 查看当前状态 |

需要留意的是，图形化操作虽然方便，但理解背后三条命令 (`add`、`commit`、`status`) 各自的作用仍然很重要。因为后续遇到更复杂的情况——比如合并冲突、撤销修改、查看历史时——界面上能提供的选项有限，最终还是需要回到命令行的逻辑来判断该怎么做。换句话说：**界面帮你省去了敲命令的麻烦，但概念本身没有变**。

理解了这三个区域和提交流程之后，还有一个问题值得深入：一次提交到底包含了什么？为什么 Git 能把它们串成一条时间线？

Git 的每一次提交，记录的远不止是文件内容的变化。每个 commit 都包含：当前所有文件的完整快照、作者信息、时间戳、提交说明，以及最重要的——**父提交的引用**。正是这个“父提交”的存在，让 Git 能把一个个独立的存档点串联成一条完整的历史链。每个提交都知道自己的上一个提交是谁，因此无论你回溯到哪个节点，Git 都能沿着这条链找到它的来龙去脉。至此，项目不再只是一个普通文件夹，而是一条可追踪、可回溯、可分叉的开发时间线。

以下查看提交历史的常用命令：

```bash
git log                  # 完整历史
git log --oneline        # 简洁一行显示
git log --graph --oneline --all   # 图形化显示所有分支
```

在 VS Code 中，提交历史并不是只能靠命令行 `git log` 才能查看。在源代码管理面板的右上角，点击“图表”按钮，就会以图形化的方式列出所有提交记录。每条记录会清晰显示提交说明、作者、时间和对应的哈希值，并且不同分支的走向也会用线条分叉直观呈现出来。这相当于把 `git log --graph --oneline --all` 的输出搬到了图形界面里，让你不用敲命令也能一眼看明白时间线的走向。对于刚接触 Git 的开发者来说，这种可视化的方式比在终端里读日志要友好得多——你能直接看到每个提交从哪来、往哪去，整个项目的时间脉络一目了然。

![VS Code 源代码管理图形视图：可视化提交历史与分支关系](https://code.visualstudio.com/assets/docs/sourcecontrol/overview/source-control-graph.png)

*上图是 VS Code 的“源代码管理”面板中的图形视图。它清晰展示了当前仓库的提交历史 (每个圆点代表一次提交) 、分支结构 (如 main 分支与 feature 分支的走向) ，以及来自远程仓库的传入更改。对于初学者来说，这个图形化界面是理解前面所讲的“提交时间线”和“分支分叉与合并”概念的最直观辅助工具。*

## 2.3 分支的原理与操作

![Git 分支示意图](git简明教程/git历史分支示意.png)

分支是 Git 最核心的设计，也是它区别于普通文件管理工具的关键所在。第 1 章曾简单提到 Git 能实现分支的创建与合并，在正式介绍相关操作之前，有必要先理解这个概念的底层逻辑。

如果你看过漫威系列电影，应该对“时间线”的分叉与交汇不陌生——Git 的分支模型正是类似的思想。一个 Git 项目默认拥有一个**主分支** (通常为 `main` 或 `master`) ，同时允许你在任何时候从它上面派生出**其他分支**。这种机制非常适合较大的功能开发或实验性修改：你可以在独立分支上自由尝试、反复提交，而完全不影响主分支的稳定性。等该分支上的任务彻底完成并通过验证后，再将其**合并**回主分支。合并完成后及时删除已用完的分支，整个提交历史便能保持干净、清晰。

对于刚接触 Git 的个人开发者而言，并不需要一上来就学习复杂的 Git Flow 工作流。**最基础的策略是：**

> **保持主分支始终稳定；每当开始一个新任务，就新建一个分支；在该分支上完成开发和本地测试；确认无误后合并回主分支，最后删除这个临时分支。**

这套轻量策略足以覆盖绝大多数个人项目及小团队协作场景，既降低了管理成本，也为后续扩展更复杂的工作流留足了空间。

### 2.3.1 分支的本质

在 Git 中，分支本质上只是一个**指向某个提交的指针** (或者说引用) 。默认的主分支通常叫 `main` (或 `master`) ，它指向最新的提交。当你创建一个新分支时，Git 只是新建了一个指针，指向当前所在的提交，并不会复制任何文件。因此，创建分支在 Git 中是极轻量的操作，几乎瞬间完成。假设我们主分支的最新提交是D，在此基础上，我们创建了`feature` 分支，则`feature` 分支和 `main` 分支指向同一个提交 D。

```text
           main
             ↓
A ← B ← C ← D
             ↑
          feature
```

当你开始在 `feature` 上提交新的改动 E 时，`feature` 指针向前移动，而 `main` 保持不变：

```text
           main
             ↓
A ← B ← C ← D
             \
              E ← F
                  ↑
               feature
```

这就是分支的工作原理：它只是移动指针，不复制文件，因此切换分支也很快。

### 2.3.2 创建与切换分支

**创建分支 (仅创建，不切换) ：**

```bash
git branch 新分支名
```

例如：`git branch feature/add-search` 会创建一个名为 `feature/add-search` 的分支，但当前仍在原分支。

**切换分支：**

```bash
# 方法一 (旧版) 
git checkout 分支名

# 方法二 (新版) 
git switch 分支名
```

例如：`git switch feature/add-search` 切换到该分支。

**创建并立即切换：**

```bash
# 方法一 (旧版) 
git checkout -b 新分支名

# 方法二 (新版) 
git switch -c 新分支名
```

`-c` 是 `--create` 的缩写，表示创建并切换。上面两条命令都等价于：

```bash
git branch 新分支名      # 创建
git switch 新分支名      # 切换
```

**为什么会有新旧两种写法？**

在早期 Git 中，`checkout` 命令身兼多职——既能切换分支，也能恢复文件、丢弃工作区改动。职责太多，一个命令干了好几件不同的事，用起来容易混淆。比如 `git checkout 文件名` 和 `git checkout 分支名` 是完全不同的操作，很容易混淆。

所以 Git 后来引入了两个更专注的命令：

- `git switch` —— 只负责切换分支
- `git restore` —— 只负责恢复文件

原来的 `checkout` 仍然保留，但新项目和个人更推荐使用 `switch` / `restore`，意图更清晰，出错的概率也更小。当然，`checkout -b` 这个写法至今仍然非常普遍，如果你已经用习惯了，继续用也完全没问题。

VS Code 也支持可视化切换分支：点击左下角的分支名，上方会弹出分支操作菜单，你可以选择创建新分支，或从列表中直接切换，比敲命令更直观。

![VS Code 分支操作菜单](https://code.visualstudio.com/assets/docs/sourcecontrol/overview/gitbranches.png)

### 2.3.3 合并分支

当你在一个分支上完成开发后，需要将其成果合并回主分支 (或其他目标分支) 。合并的本质是**将两个分支的历史结合起来**。

**执行合并：**

```bash
git switch main           # 先切换到目标分支 (接收改动的一方) 
git merge feature/add-search   # 把 feature/add-search 合并到当前分支
```

合并有两种常见情况：

1. **快进合并 (Fast-forward) **：如果目标分支 (如 `main`) 自创建 `feature` 分支以来没有新的提交，那么 Git 只需将 `main` 指针直接移动到 `feature` 的最新提交上，相当于“追赶”上去。这种方式不会产生新的合并提交。

2. **三方合并 (3-way merge) **：如果目标分支和 `feature` 分支在分叉后都有了各自的提交，Git 需要找到两个分支的**共同祖先**，然后将两边的变更合并到一起，生成一个新的合并提交。这种方式更常见，也可能会遇到冲突。

**处理冲突：**

当两个分支修改了同一文件的同一部分时，Git 无法自动合并，会提示冲突。此时需要手动编辑冲突文件，删除 `<<<<<<<`、`=======`、`>>>>>>>` 标记，保留最终需要的版本，然后：

```bash
git add 冲突文件
git commit -m "Merge branch 'feature' into main"
```

> **冲突的产生与预防**
>
> 冲突并不是 Git 的缺陷，而是团队协作中的正常现象。当两个人同时修改了同一个文件的同一区域时，Git 无法自动判断该保留谁的改动，就会产生冲突。
>
> 虽然冲突无法完全避免，但良好的开发习惯可以显著减少冲突的发生频率：
>
> 1. **分支周期简短**。分支存在的时间越长，与主分支的偏差就越大，合并时越容易产生冲突。完成一个小功能就及时合并，而不是等所有功能全部做完。
> 2. **定期将主分支的更新合并到当前分支**。当团队其他人有代码合并到主分支后，及时把这些更新拉到自己的分支上，避免开发周期内与主分支差异过大。
> 3. **确保每次合并前先测试通过**。无论是合并到主分支，还是将主分支合并到当前分支，都应该先确保代码能正常运行。
>
> 简单来说，冲突不可怕，可怕的是怕冲突而不敢合并。**合并频率越高，每次冲突的规模就越小，解决起来也越轻松。**
>
> 当然，对于单人开发者而言，工作流可以更加简化——每次都在独立分支上开发，完成后合并回主分支，再基于更新后的主分支拉出新分支继续下一项工作。这样主分支始终保持稳定，同时也避免了多分支并行带来的冲突风险。

### 2.3.4 删除分支

分支合并后，它的任务已经完成，可以删除以保持仓库整洁。

**删除本地分支：**

```bash
git branch -d 分支名
```

如果分支还未合并，`-d` 会报错，可以用 `-D` 强制删除 (谨慎使用) 。

**删除远程仓库的分支：**

```bash
git push origin --delete 分支名
```

删除分支只是删除了指针，不会删除提交历史。只要分支已经合并，历史仍然保留在主分支中。

## 2.4 远程仓库操作

前面我们提到，GitHub 可以为你的项目提供远程备份、跨设备同步和协作能力。但要在本地 Git 和远程 GitHub 之间建立联系，就需要掌握几个核心的远程操作。这些操作并不复杂，但它们将你的本地时间线延伸到云端，让代码不再局限于单台电脑。

作为分布式版本控制系统，Git 的每个本地仓库都包含完整的历史记录，远程仓库 (如 GitHub 上的仓库) 则是一个共享的“中央”节点，用于同步各方的改动。以下介绍最常用的四种远程操作：关联、推送、拉取和克隆。

要使用 GitHub 作为远程仓库，首先需要有一个 GitHub 账号，并确保能够正常访问 GitHub 网站。国内稳定访问的方法可以参考 {% post_link Windows效率神器推荐-Wox-Markdown编辑器与GitHub加速器配置指南 %}。GitHub 账号的注册流程详见 {% post_link 个人博客搭建指南：基于-GitHub-Pages-的完整流程 %} 第二章。

### 2.4.1 关联远程仓库

在 GitHub 上创建一个空仓库后，将其与本地仓库关联：

```bash
git remote add origin https://github.com/用户名/仓库名.git
```

origin 是 Git 为远程仓库设置的默认别名，绝大多数项目都沿用这一约定，当然也可以按需使用其他名称。

查看已关联的远程仓库：

```bash
git remote -v
```

### 2.4.2 推送与拉取

**推送 (Push) **：将本地分支的提交上传到远程仓库。

首次推送某个分支：

```bash
git push -u origin 分支名
```

`-u` 表示建立本地分支与远程分支的跟踪关系，后续推送可直接用：

```bash
git push
```

**拉取 (Pull) **：从远程仓库下载更新并合并到当前分支。`git pull` 实际上是 `git fetch` (下载更新) 和 `git merge` 的组合。

```bash
git pull
```

如果你只是想查看远程有哪些更新而不自动合并，可以使用 `git fetch`。

VS Code 也提供了对应的图形化操作界面：

![VS Code 远程仓库](https://code.visualstudio.com/assets/docs/sourcecontrol/overview/incoming-outgoing-changes.png)

### 2.4.3 克隆仓库

如果你要参与一个已有的远程项目，或者想在自己的另一台电脑上获取代码，可以直接克隆：

```bash
git clone https://github.com/用户名/仓库名.git
```

克隆会自动将远程仓库完整复制到本地，并创建 `origin` 远程别名，同时检出 `main` 分支。

## 2.5 个人开发工作流 (本地与远程) 

对于个人开发者，建议采用一套极简的分支策略：**主分支始终保持稳定，每个新任务新建一个分支，完成后合并回主分支，最后删除任务分支。**

### 不使用 GitHub (纯本地) 

```bash
# 开始新任务
git switch main
git switch -c 任务名

# 写代码，多次提交
git add .
git commit -m "说明改动1"
# ...
git add .
git commit -m "说明改动N"

# 自查无误后合并
git switch main
git merge 任务名
git branch -d 任务名
```

### 使用 GitHub (含远程同步) 

```bash
# 开始新任务
git switch main
git pull                     # 确保本地主分支是最新的
git switch -c feature/任务名

# 写代码并提交
git add .
git commit -m "说明改动"
git push -u origin feature/任务名   # 首次推送并建立跟踪

# 继续开发，多次提交推送
git add .
git commit -m "说明改动"
git push

# 自查无误后，个人项目可以本地合并
git switch main
git pull                     # 拉取最新主分支
git merge feature/任务名
git push
git branch -d feature/任务名
git push origin --delete feature/任务名
```

对于团队项目，合并通常不是在本地直接执行，而是在 GitHub 上创建 Pull Request，经过代码审查后再合并。

## 2.6 小结

**常用命令速查**

| 命令 | 用途 |
| --- | --- |
| `git status` | 查看当前工作区和暂存区的状态 |
| `git add 文件名` | 暂存指定文件 |
| `git add .` | 暂存当前目录下所有改动 |
| `git commit -m "说明"` | 创建一次提交 |
| `git log --oneline` | 简洁查看提交历史 |
| `git log --graph --oneline --all` | 图形化显示所有分支历史 |
| `git switch 分支名` | 切换分支 |
| `git switch -c 新分支名` | 创建并切换到新分支 |
| `git merge 分支名` | 把某个分支合并到当前分支 |
| `git branch -d 分支名` | 删除已经合并的本地分支 |
| `git remote -v` | 查看远程仓库地址 |
| `git push` | 推送到远程仓库 |
| `git pull` | 拉取远程仓库更新 |
| `git clone 仓库地址` | 克隆远程仓库到本地 |
| `git diff` | 查看工作区中未暂存的改动 |
| `git diff --staged` | 查看暂存区与最新提交的差异 |
| `git restore 文件名` | 撤销工作区对文件的修改 (**不可恢复，谨慎使用！**)  |
| `git restore --staged 文件名` | 将文件从暂存区移出 (保留工作区改动)  |

该表格仅供速查，无需死记硬背所有命令，而是需要明确**工作主线**：

```text
新任务 -> 新分支 -> 多次提交 -> 自查 -> 合并回 main -> 删除任务分支
```

把这套流程走顺，Git 就已经能覆盖大多数个人项目的日常管理需求了。

# 3. 附录：常见误区

## 3.1 “只有团队协作才需要 Git”

恰恰相反，个人开发反而更容易需要 Git。因为没有人帮你记录改了什么，也没有人帮你恢复误删的内容。Git 对个人开发者最大的价值就是：让你敢改、敢试、能回退。

## 3.2 “必须等完整功能做完才能提交”

不需要。提交是存档点，不是发布版本。只要改动相对清晰、以后自己能看懂，就可以提交。

更准确的理解是：

- **提交** 记录一段工作进度；
- **分支** 承载一项任务；
- **合并** 表示这项任务进入主线。

## 3.3 “所有文件都应该提交”

并非如此。源代码、配置文件模板、文档、必要资源应当提交；而临时文件、缓存、大型构建产物、密码、令牌、私钥等则不应纳入版本控制。

## 3.4 “分支越多越专业”

分支并非越多越好。对个人开发者而言，每个任务对应一个分支即可。功能完成后及时合并并删除分支，仓库历史会保持整洁。

# 总结

Git 的本质不是“上传代码”，而是管理项目历史。它通过提交记录代码状态，通过分支让不同任务并行推进，通过合并将完成的工作整合回主线。

对个人开发者来说，最推荐的学习顺序是：

1. 先理解分支模型，建立“分支即任务”的工作思维；
2. 学会在 VS Code 里查看改动、暂存文件、写提交说明；
3. 养成“新任务开新分支、经常提交、完成后合并”的习惯；
4. 最后再学习 Pull Request、冲突处理、回滚、标签、发布等进阶内容。

不必一开始就掌握所有 Git 命令。先把项目历史记录清楚，把主分支保护好，让每一次改动都成为可追踪的记录——这就是 Git 带给开发者最重要的价值。
